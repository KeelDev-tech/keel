# Keel 0.14 configured runtime recovery

The recovery module preserves an **explicitly configured set of Keel stores**
under the shared operational write barrier. It is an offline copy and restore
facility. It does not start a controller, contact Muse, renew an approval, retry
a browser action, clear a hold, or declare the external application state known.

`configured_state_complete=true` means that every store and file in the
operator's accepted inventory was captured and verified. It does **not** mean
that Keel discovered every store on the host. `inventory_completeness_authenticated`
and `checkpoint_authority_authenticated` remain false. The operator must account
for additional application stores, original context files, credential stores,
qualification captures and any other required host state before using that
inventory as a recovery plan.

## Supported inventory

Every store uses a separate, nonoverlapping, private `0700` directory. Its
regular files must be owned by the current user, singly linked and `0600`.
Unknown files inside a configured store block capture rather than being silently
omitted. Known SQLite `-wal`, `-shm`, and `-journal` files are validated but not
copied: SQLite's online backup materializes the committed database contents.

| Kind | Captured state |
|---|---|
| `control` | `control.sqlite3`, `control.key`; `control.lock` is recreated empty |
| `native_session` | `native-session.sqlite`, `native-session.key`, including approved attachment payloads, receipts and pending dispatch |
| `operational_runtime` | `operational-runtime.sqlite3`, `operational-runtime.key`; session/qualification bindings and shared intent associations |
| `sources` | `sources.sqlite3`, `store.identity`, all `attachments/objects/<sha256>` objects; source revisions, approval requests, decisions and revocations remain in the database |
| `temporal` | `temporal.sqlite3`, including all claim, observation, dependency and approval-observation history; this version of TemporalMemory has no separate key |
| `coordinator` | `coordinator.sqlite3`, `coordinator.sqlite3.key`; task, inbox, lease and stop state |
| `recovery` | `recovery.sqlite3`, `recovery.sqlite3.key`; job, approval, revocation, UNKNOWN and 429 state |
| `agent` | `agent.sqlite3`, `agent.sqlite3.key`, `reviews.sqlite3`; LocalState jobs, attempts, approvals, snapshots and review records |
| `skills` | The contiguous `event-00000000.json` workshop history; chain hashes checked |
| `canonical_sqlite` | One explicitly named database and optional explicitly named key; opaque integrity preservation, without inferring application semantics or authorization |
| `canonical_files` | An exact mapping of relative filenames to expected SHA-256; opaque bytes only, with no inferred canonical authority |

All historical attachment references are checked against actual bytes and size.
Unreferenced content-addressed attachment objects are retained as well; capture
does not perform garbage collection. Required canonical store IDs must identify
`sources`, `agent`, `canonical_sqlite` or `canonical_files` stores. An empty or
absent canonical list prevents a completeness claim.

The bounds are 64 stores, 8 MiB per file/database logical contents, 64 MiB total,
and 8,192 enumerated files per store. A larger host needs an explicitly reviewed
extension; exceeding a bound fails visibly.

## Trusted configuration and Python API

The inventory is supplied by trusted host integration code, not generated by a
model as authority. `source_sha256` pins the release/configuration identity the
host intends to restore. Paths are local placement and are excluded from the
portable inventory hash; all store IDs, kinds, selectors and content pins remain
bound. Order of the stores is normalized.

```json
{
  "schema": "keel.operational.runtime-inventory.v1",
  "workspace_id": "my-workspace",
  "source_sha256": "<64 lowercase hexadecimal characters>",
  "writer_coordination": "control_barrier",
  "stores": [
    {"store_id": "control", "kind": "control", "home": "/private/runtime/control"},
    {"store_id": "sources", "kind": "sources", "home": "/private/runtime/sources"},
    {"store_id": "native-1", "kind": "native_session", "home": "/private/runtime/native-1"},
    {"store_id": "runtime-1", "kind": "operational_runtime", "home": "/private/runtime/runtime-1"}
  ],
  "required_store_ids": ["control", "sources", "native-1", "runtime-1"],
  "canonical_store_ids": ["sources"],
  "external_state": ["muse-browser", "employer-service"]
}
```

Every configured store must be in `required_store_ids`. A canonical SQLite entry
also has `database` and `key` (a filename or `null`). A canonical-files entry
also has `files`, mapping each relative filename to its expected raw SHA-256.

```python
from keel_operational.control import StopLedger
from keel_operational.recovery import checkpoint, snapshot, restore

# Opens an already provisioned ledger without starting any worker.
control = StopLedger("/private/runtime/control", "my-workspace")
current = checkpoint(config, control=control)
saved = snapshot(config, "/private/backups/checkpoint-001",
                 control=control, expected_checkpoint=current)

# Retain current and saved["manifest_sha256"] separately from the backup.
# Restore requires the actually current authoritative record, not simply a
# checkpoint read back from the old backup itself.
receipt = restore("/private/backups/checkpoint-001", "/private/restored-001",
                  authoritative_checkpoint=independently_retained_current,
                  expected_manifest_sha256=independently_retained_manifest_pin)
```

`checkpoint` and `snapshot` acquire `StopLedger.maintenance()` internally. Do not
wrap them in `control.writer()`: shared-to-exclusive acquisition would deadlock.
All mediated mutations, including a wrapper's entire multi-store sequence, must
hold `control.writer()`. Baseline components are unchanged and do not magically
acquire the new barrier; the host must route their writes through that wrapper.
The CLI exposes equivalent checkpoint/snapshot/restore operations; see
`OPERATIONAL_CLI.md` for its concrete arguments.

## What consistency means

The exclusive barrier waits for participating local writers and blocks new ones.
The capture pins complete SQLite schema, table rows and persistent metadata
(`user_version`, `application_id`, `schema_version`, encoding and auto-vacuum),
plus exact regular-file hashes. It takes repeated before/after views and validates
the copied views against the original logical checkpoint. Different SQLite page
layouts cannot conceal different logical state or migration versions.

Authenticated passive readers verify control, native, runtime, recovery and
coordinator journals. Temporal event hashes and source identity/event/attachment
bindings are checked. Each runtime metadata record must bind to exactly one
captured native session with matching configuration and source pin. Associated
shared-ledger attempt bindings and tokens must agree. A `PREPARING` record before
shared admission is a valid interrupted commit gap and remains unresolved.

This is a consistent cut among **participating writers**, not a transaction
across unrelated services. An already issued native tool can still finish while
the filesystem is quiescent. Its intent and uncertainty are preserved. An
unmanaged writer or filesystem owner can bypass local coordination; observed
changes cause rejection, but matching snapshots cannot prove no unseen writer
exists. Hashes and host keys also do not authenticate original factual evidence,
human identity, platform permission, or the external authority's freshness.

## Offline restore and interruption

Restore rejects existing destinations and destinations anywhere inside the backup.
It validates the external checkpoint and exact manifest before creating output.
The destination immediately receives `OFFLINE_RESTORE.json`, before any runtime
store is published. This marker fences operational wrapper dispatch even if
copying is interrupted. `RESTORE_VERIFIED.json` is written only after all captured
stores and cross-bindings match the expected checkpoint. A partial directory
without that final receipt must not be used as a completed restore.

The offline marker remains after verification. Use an explicit recovery review,
fresh source and approval checks, and a newly qualified native browser session
before starting new work. Never remove the marker just to make an old workflow
continue. An ISSUED/UNKNOWN intent is not replayable permission; restoration does
not reconcile it, observe a lost receipt, or prove that the employer did not
receive an action. Muse/browser state, remote service state and native permission
grants are not restored.

Backups contain private state and host authentication keys. Keep them in private
storage and retain the authoritative latest checkpoint separately. The module
does not add encryption, a remote key service, automatic offsite upload or a new
paid dependency.

## Executed fixture coverage

`demo(home)` creates ten real configured store directories, synthetic source
records and actual attachment bytes, a synthetic approved-then-revoked decision,
an interrupted native preparation, a shared 429, a recovery UNKNOWN, temporal
history, a coordinator stop, skill events and LocalAgent review/state stores.
It backs up and restores those stores, verifies the common checkpoint and returns
eleven measured checks. No actual browser, Muse account, model or employer is
called. Focused tests additionally exercise opaque SQLite/blob/special filename
round trips, migration metadata drift, writer exclusion, changed inputs, missing
files, symlinks, hardlinks, stale authority, tampering and interrupted restore.
