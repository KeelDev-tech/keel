# Screening evidence and verification holds

Launch packets carry structured form intelligence and bounded posting text into the exact prescreen input. A valid PARK veto prevents packet publication and sealing. An older active packet is archived when screening or sealing prevents a rebuild.

Missing, malformed, incomplete or mismatched evidence blocks preparation and promotion. It remains verification work: packet construction raises PacketEvidenceUnavailable, releases the launch lock, and does not manufacture an applicant-input question. Pre-promotion checks raise VerificationUnavailable; legacy re-screen reports verification_hold and leaves the pending-verification entry unchanged. Complete evidence exposing an actual applicant commitment or attestation still routes through PARK and the applicant-input path.

Form evidence must identify the exact HTTPS application URL, mark extraction_complete=true, have no unresolved rendered options, and remain within 500 questions, 100 options per question, 500 characters per label/option and 512 KiB serialized data. Screening preserves each accepted option in full. Posting text must be non-empty and at most 50,000 characters, with posting_text_url exactly matching the application URL. Stored queue posting_text/description without this binding remains verification work; do not backfill a binding merely because a row has an application URL. The trusted live-promotion caller supplies one fetched text snapshot for the URL passed to the screen. This association is not source authentication. Oversized fetched text is rejected rather than silently truncated before screening. Queue description/posting fields are preparation inputs, not proof of freshness or source authenticity; live promotion uses one fetched snapshot for both screens.

Greenhouse marks extraction incomplete when an observed non-material label cannot be parsed or a dropdown still requires rendered options. Lever requires an explicit customQuestions list and a successful hosted-page check; missing API fields and failed hosted checks remain incomplete. These HTTP markers cover observed adapter fields only. They do not prove observation of every dynamic, hidden, unlabeled or future provider control. Required dropdown/select/radio/multiselect fields without any nonblank observed choices are incomplete even if the adapter forgot its unresolved-options marker. Receiving executors must independently inspect the current rendered form and enforce the human approval contract.

Hypothesis is a pinned development dependency only. Its bounded synthetic cases run offline with no saved example database. CI installs requirements-validation.lock on Python 3.11 and 3.12 and explicitly runs the evidence regressions. The standard-library runtime does not import Hypothesis. This change neither authorizes submission nor qualifies the private executor or live ATS compatibility.

Default pre-promotion screening reloads KEEL_HOME/data/answer_bank.json on each call. It uses packet_contract.confirmed_answers for the exact role and employer, admitting only unchanged, unexpired, in-scope applicant assertions. It never falls back to engine/example answers. Malformed banks become UNKNOWN; missing banks supply no answers. Unreceipted banded rules cannot clear this promotion screen. Explicit answer_bank injection remains a trusted caller/testing seam. Answer correction does not itself promote a queue entry, clear an independent attestation, or authorize execution.
