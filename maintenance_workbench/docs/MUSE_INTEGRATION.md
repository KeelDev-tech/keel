# Integration into the existing MUSE/KEEL environment

## First integration: a read-only developer task

Restore the text bundle into a NEW review directory, verify the restored tree,
and run its own tests and synthetic demo. Nothing in the file handoff constitutes
production cutover approval. Keep this separate from the live executor source.

Inspect the current actual repository and accepted directives before connecting
anything. The reference allowlist is for KEEL 0.3.1's public review layout. Do not
reuse it blindly for ~/workspace/job-pipeline/engines/application-executor/ or a
newer branch. Missing files must fail; do not quietly search a different checkout.

Give the maintenance task an approved narrow allowlist, a quiescent source copy,
and a new private output directory. Start with documentation, interface definitions,
selected implementation files and protected synthetic tests. Do not include .env,
keys, browser sessions, operational ledgers, live answer-bank content or queue
state merely because the task can see the parent directory.

The existing scheduler may invoke the shipped CLI only through its existing
sanctioned mechanism. This package creates no schedule. Store its evidence pointer
and status in the existing control plane through that plane's approved writer;
do not point this package directly at live JSONL logs or database tables.

## Agent responsibilities

The evidence worker selects applicable source and preserves source references.
The maintenance worker proposes exact replacements bound to the captured revision.
The local recipe runner performs its fixed analysis/check operations. The reviewer
uses the existing authority system to decide what happens next. An executor with
existing permissions, not this package, would perform a separately reviewed future
integration. These names describe responsibilities, not independently authenticated
identities. Distinct roles sharing all OS permissions are not independent review.

## Native runtime testing and release are later integration steps

This build refuses arbitrary target-code execution. A real OS-isolated target-test
adapter, authenticated release integration, upstream release/advisory polling,
service-credential separation, and real-provider/sandbox validation remain separate
work. They are not marked PASS. Do not substitute unrestricted subprocess execution
because Podman or another sandbox is unavailable. Do not install or download a
model, container image, paid fallback, or service automatically.

Retirement is simple: remove this review task and its private derived outputs under
the existing retention policy. There is no canonical-state migration to reverse.
Never delete unrelated backups, canonical receipts or original telemetry.
