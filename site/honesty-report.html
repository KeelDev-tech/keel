The Count

What the number is

A private production pipeline — the one Keel's discipline was built to run — holds 208 rows in its application ledger in canonical SUBMITTED status, as counted on 2026-09-23. "Verified submissions" has exactly one definition here: ledger rows whose status is SUBMITTED, and the pipeline's own reporting rule records that status only on explicit page-confirmation evidence — the confirmation the application page itself shows. Nothing counts because a worker said it tried; nothing counts on a 200 OK; nothing is projected, extrapolated, or rounded up.

Method

How the recount works

The public repo ships geo-pipeline/recount.py, the same script that produces the published figures. It reads two private sources — the production ledger (application-ledger.json) and the append-only telemetry log (telemetry/events.jsonl) — and outputs aggregates only. No identifying detail ever leaves the private side.

The recount is deliberately boring:

Canonical status match. A row counts as SUBMITTED under the canonical ledger-status aliasing (a naive exact-string match once undercounted 209 to 207 because two historical rows were lowercase; the cross-check now uses the same canonicalizer on both sides, and the run fails if they disagree).

Two-way cross-check. A direct row count and the evidence-audit reader must agree to the row, or the recount aborts with no write.

Fail closed. Any source read error produces a non-zero exit and no partial write; stats.json is written atomically (temp file + rename). Gate figures are distinct (lead, gate) pairs in gate_blocked events, with backfilled pairs deduped on the pair and TEST- fixtures excluded.

No re-verification. The recount counts the ledger; it does not re-verify confirmations. A count that re-interpreted history would not be a recount. The launch figure of 55 (counted 2026-09-15 00:17 PT) is a historical canon and is never recomputed.

Full methodology: docs/data-story.md. Machine-readable canon: docs/geo/stats.json — regenerated by recount, never hand-edited.

Limits

What you cannot independently verify

Honesty requires stating the checkability boundary plainly:

You cannot rerun the private pipeline. The ledger rows, the confirmation artifacts, and the execution layer that submitted them stay private by design — publishing submission fingerprints would get the pipeline blocked by ATS vendors (SPLIT.md). A reader of this repo cannot independently replay the 208 submissions or re-inspect the quoted confirmations. The recount script is public; its inputs are not.

The public repo makes no submission claims of its own. Keel the public project is the tools, the gates, and the telemetry discipline — the machinery that made "only ever claims what you tell it is true" operational. The 208 figure belongs to the private production pipeline that used this exact discipline; the public repo did not produce it.

The weakest rows are named on purpose. The 6 unevidenced rows are part of the 208, disclosed here rather than silently excluded. If that bothers you, it should — that discomfort is the grade working as designed.

Eligibility is not claimed either: Keel is free and open source (Apache-2.0), ships no accounts, no quotas, and no paid tiers. Anything that would cost money or misrepresent eligibility is outside its contract — see the truthfulness contract.

Refusals

The other number: what never shipped

Honest automation is measured in refusals. In the same recount, 3,427 leads were stopped by a gate rather than shipped with a lie — including 4 where the fabrication gate tripped specifically because the system refused to invent an answer. Needs-input parks (488), unmappable required questions, unverifiable postings (15), travel commitments never signed by a bot, essays never ghostwritten. The full per-gate table is in stats.json.
